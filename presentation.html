1 项目概览

这是什么？

一个面向硬件工程师的 AI Agent 驱动 PCB 元器件库。 用户用自然语言输入（"0805 封装 10kΩ 电阻库存多少"）， 系统自动翻译为 SQL 并返回结果。支持查询 + CRUD + 选型建议。

3 CLAUDE.md & SPEC.md — AI 编码的"宪法"

核心思想：人类开发者有 Coding Standard，AI Agent 也需要。CLAUDE.md 和 SPEC.md 就是给 Claude Code 看的编码宪法和技术规格书——让 AI 在正确的约束下工作，而非"自由发挥"。

🎨 frontend/CLAUDE.md — 前端技术约定

🌐 根 CLAUDE.md — 5 条军规

  1. 编码前思考：<thinking> 标签暴露思路 · 遇歧义即阻断 · 评估影响半径
  2. 简洁优先：标准库优先 · 奥卡姆剃刀 · 不过度防御编程

4 Git 工作流与版本纪律

4.1 Git 是 AI Coding 的天然搭档

AI 辅助编程有一个核心矛盾：AI 写得快，但可能写错。Git 恰好解决了这个问题——它提供了一张随时可用的"撤销"网。两者互补，缺一不可。

AI 编程的天然风险

  • AI 一次生成大量代码，人工逐行审查跟不上
  • AI 可能"顺手"改不该改的文件（风格、import、空行）
  • 多轮对话中，AI 可能遗忘之前的约定
  • 一次错误的修改可能连锁影响多个模块

Git 提供的保护

  • git diff — AI 的每一次修改都无处遁形，逐行审视
  • git reset --hard — AI 改坏了？一秒回到修改前
  • git log — 追溯每次 AI 协作的来龙去脉
  • git bisect — 定位是哪个 AI 改动引入了 bug
一句话：Git 让你敢于让 AI 放手干活——因为你知道任何改动都是可逆的。没有 Git 的 AI 编程是走钢丝，有了 Git 就是踩在地面上。

5 核心引擎：三层 NL2SQL 架构

前四章讲了工具链和工程规范。这一章讲项目的核心——NL2SQL 引擎。它只做一件事：用户说人话，它输出 SQL，执行后返回结果。它不是 chatbot，它是数据库查询翻译器。

三条路径，按优先级：

  1. 规则引擎（<1ms）—— 6 类正则匹配封装/分类/制造商/库存/价格/料号，覆盖 80% 查询
  2. 缓存层（<1ms）—— 问过的问题直接返回上次 SQL，30 分钟有效
  3. LLM（1~3s）—— 规则和缓存都兜不住时，才调用大模型理解复杂语义

LLM 不是第一选择，是最后一道防线。下一章（第 6 章）展开讲 LLM 被调用时收到的 5 层 Prompt 是怎么设计的。

5.2 搜索模式：Fast vs AI

80% 的查询是"封装 + 分类"模式（"0805 电阻"、"SOT-23 MOS管"），正则毫秒级覆盖。只有复杂语义才走到 LLM。

⚡ 快速模式 (Fast)

规则 → 缓存，全毫秒级。未命中直接返回空 + 建议切换 AI。
零 AI 调用、零成本。

🤖 AI 模式 (Smart)

规则命中 → 调 LLM 给选型建议；规则未命中 → LLM 生成 SQL。
智能建议 + 替代物料推荐。

6 提示词与上下文管理

上一章讲了引擎的三条路径，LLM 是最后一道防线。这一章展开：当 LLM 被调用时，它收到的 Prompt 是怎么设计的——不是一段话，而是 5 层信息精确叠加。

6.1 5 层 Prompt 各干了什么

每次 LLM 被调用时，实际发给它的内容是：

SYSTEM PROMPT
P1 你是 PCB 元器件数据库助手。数据库有两张表：component_library（物料）和 component_category（分类）。当前有 27 个物料，封装包括 0805/SOT-23…
→ 告诉 LLM "数据库里有什么"，确保它生成正确的表名和列名
P2 必须输出纯 JSON：{"sql": "...", "explanation": "...", "type": "SELECT", "suggestion": "..."}。不要 Markdown 包裹。
→ 告诉 LLM "按什么格式输出"，确保返回结果可被代码解析
USER MESSAGE
P3 请将以下自然语言转换为 SQLite SQL：0805 电阻库存低于 50
→ 传递用户原话，不含任何规则——所有规矩都在 System Prompt 里
P4 SQL 执行后调用
"查到了 5 款 0805 电阻。分析结果，给选型建议。只输出文字，不要 SQL。"
→ 结果解读：选型建议、替代物料推荐
P5 SQL 报错时调用
"上次 SQL 报错：no such column: price。请修正。"
→ 自我纠错：错误信息 + 原 SQL 喂回 LLM，最多 2 次

6.2 P1 是怎么工作的：动态构建 + 缓存

P1 是 5 层中唯一动态生成的 Prompt。它不在代码里写死——每次调用都从数据库实时拉取分类、封装、制造商、物料样本，组装成 System Prompt。这确保 LLM 看到的永远是当前数据库的真实快照。

构建：读文件 + 查数据库 + 拼装

buildContext() {
  schemaSQL = readFile('schema.sql')     // 静态 DDL
  categories   = db.exec('SELECT ...')   // 13 个分类
  footprints   = db.exec('DISTINCT ...') // 所有封装

  → 拼装为 ~3700 chars 的 System Prompt
}

缓存：5 分钟 TTL，避免重复查询

getContext() {
  if (缓存未过期) return 缓存       // 命中 → 0 次 DB
  return buildContext()              // 过期 → 重建
}
// 新增物料后最多 5 分钟
// LLM 就能看到新数据

7 安全设计：写操作的三道防线

引擎能生成 SQL 了，但 LLM 生成的 SQL 能直接执行吗？不能。从 NL 输入到 SQL 执行之间，经过三道安全防线。

NL 输入
→
① 写意图检测

→
② LLM 生成 SQL
→
③ SQL 守卫
DDL/多语句/无WHERE
→
④ 前端确认弹窗

SQL 守卫 (sql-guard.js)

function guard(sql) {
  // 禁止 DDL
  if (/DROP|TRUNCATE|ALTER|CREATE/i.test(sql))
    throw Error('禁止 DDL');

  // 禁止多语句
  if (/;\s*(?=\S)/.test(sql))
    throw Error('禁止多语句');

  // DELETE/UPDATE 必须带 WHERE
  if (/^DELETE/i.test(sql) && !/WHERE/i.test(sql))
    throw Error('DELETE 必须有 WHERE');
  if (/^UPDATE/i.test(sql) && !/WHERE/i.test(sql))
    throw Error('UPDATE 必须有 WHERE');
}

确认弹窗设计

  • 展示自然语言解释（LLM 生成的人类可读描述）
  • SQL 默认折叠，点击"查看 SQL ▸"展开
  • 显示操作类型 + "AI 生成 · 请核实后确认"
  • 用户点击"确认执行"才调 /api/query/execute
  • 取消 → 丢弃 SQL，不执行任何操作
